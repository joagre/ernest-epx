# Defects found in epx

The defects the library met in epx, each written as a report for epx's tracker, found 2026-10-20 while the first cut was tried against the NIF (`docs/log.md`, *The first cut built*), 7 and 8 by the release review the same day. Each stays until a release of epx the library builds has its fix. `sub` and `scroll` of the proposal wait on the first three.

1. **A sub-pixmap has no transformation set.** `epx_pixmap_init_sub_pixmap` never sets `ltm` and `ctm`, so every coordinate operation on a pixmap `pixmap_sub_pixmap/5` made reads uninitialized memory: `epx:pixmap_get_pixel(epx:pixmap_sub_pixmap(P, -1, -1, 2, 2), 0, 0)` crashed the VM. The fix is `epx_t2d_identity(&dst->ltm); dst->ctm = &dst->ltm;` in the initializer.
2. **A scroll by more than the width is unbounded.** `epx_pixmap_scroll_left` and `epx_pixmap_scroll_right` take any `amount`, and one past the pixmap's width reads and writes outside it: `pixmap_scroll/6` with a horizontal shift past the width crashed or aborted the VM.
3. **A vertical scroll writes by the source's height.** `scroll_up` and `scroll_down` write into the target by the source's height, not the target's: a scroll down into a smaller target crashed the VM, and a scroll up wrote past it.
4. **`pixmap_put_pixels` reads past short data.** Given bytes short of `width` times `height` pixels by less than one pixel, it reads past the binary's end; short by a pixel or more, it writes nothing and answers `ok`. A parsable but unsupported format name, `foo`, crashes the VM where `pixmap_create/3` raises `badarg` for the same name.
5. **An empty `pixmap_get_pixels` answers live memory.** `pixmap_get_pixels(P, 0, 0, 0, 0)` answers a binary over the pixmap's own memory, padding included, whose bytes change as the pixmap is written.
6. **`epx_clip_both` cuts the source without moving the target.** An area operation whose source rectangle begins left of or above the source's clip has the rectangle cut to the clip, but the target's corner stays, so the pixels land where the cut-off part would have: `pixmap_copy_area(S, T, -1, 0, 0, 0, 3, 1)` puts the source's pixel 0 at the target's pixel 0 instead of 1. The library states where the pixels land and leaves it as epx has it.
7. **A pixmap's bytes are counted in 32 bits, and a pixel's address in an `int`.** `epx_pixmap_init` computes `bytes_per_row*height` in `unsigned int`, so a pixmap of 4 GiB or more is allocated short: `pixmap_create(65536, 65536, argb)` allocated 15 bytes, and its first write aborted the VM. `EPX_PIXEL_ADDR` computes `y*bytes_per_row + x*bytes_per_pixel` in `int`, so a pixel past the first 2 GiB is written outside the pixmap: a write to the last row of `pixmap_create(32768, 16385, argb)` crashed the VM. The library refuses a pixmap of 2 GiB or more.
8. **A rectangle's right edge is computed in `int`.** `epx_rect_right` computes `x + width - 1` in `int`, so a rectangle whose edge passes 2^31 − 1 wraps and is taken as empty: `pixmap_fill_area(P, 1, 0, 2147483647, 1, Color)` wrote nothing on a pixmap three pixels wide, where it covers pixels 1 and 2. A coordinate and a size reach epx as a `float` through the pixmap's transform, exact to 2^24, and the library bounds both at 2^24, within which the edge stays an `int`.
