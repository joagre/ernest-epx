# Defects found in epx

The defects the library met in epx that its pinned commit has not fixed, each written as a report for epx's tracker, as first filed and numbered 2026-10-20 to 2026-11-08 (`docs/log.md`, *The first cut built*, *The reports verified*, *The fixes verified*, *The sentences for 3fdacef*). The numbers are those of the first filing, which the design and the log cite; a report goes when the submodule moves to a commit that has its fix (the log's *The pin moved*), so the gaps are what epx fixed.

Each of these stays until a commit of epx the library builds has its fix.

None blocks a function of the library: each is a wart the library ships around. 33 was found 2026-10-23 trying the edges of `sub`, `scroll`, the rounded rectangle and the polygon (`docs/log.md`, *The four functions*), and 39 to 41 on 2026-11-08 at `3fdacef`, the commit the pin moved to that day (`docs/log.md`, *The sentences for 3fdacef*).

## Warts

Most serious first: 39 and 41 write wrong where a program cannot tell, each where the library scrolls or scales; 40 crashes beyond the library's bounds; and 33 takes a channel it should refuse, on a call the library never makes.

39. **A scroll between two pixmaps by both amounts shifts the whole target horizontally.** `epx_pixmap_scroll` (`epx_pixmap.c`) scrolls vertically from the source into the target within their common area, then horizontally on the target alone, whose common area with itself is the whole target: `pixmap_scroll(S, T, 1, 1, false, Fill)` with `S` a numbered 2 by 2 and `T` a 4 by 4 filled with one color left every row of `T` shifted right by one and its column 0 filled, rows 2 and 3 among them, and with `true` every row wrapped across all four columns. A target no wider and no taller than the source is right. The library states it (`design.md` §4). Found 2026-11-08 at 3fdacef.
41. **`pixmap_scale` leaves its last rows black at a large height.** `epx_pixmap_scale_area` (`epx_pixmap.c`) steps the source's row by a `float` increment once a target row, `ysf += ys`, and the accumulated error carries the last rows past the source's edge, where `epx_interp` answers transparent black: a 4 by 4 pixmap scaled into 4096 by 70000 has its last two rows `{0, 0, 0, 0}`, into 4096 by 131072 none, into 131073 one and into 140000 two. The library states no pixel rule for `scale` (`design.md` §4). Found 2026-11-08 at 3fdacef.
40. **`pixmap_fill_area` computes its address in an `int`.** `epx_pixmap_fill_area` (`epx_pixmap.c`) takes `pixmap->data + r.xy.y*wb + r.xy.x*psz` with `wb` and the coordinates `int`, where every other function takes `EPX_PIXEL_ADDR`'s `ptrdiff_t`: on a 4096 by 140000 argb pixmap, 2.29 GB, `pixmap_fill_area(P, 4093, 139997, 2, 2, C)` crashed the VM, and on a 4096 by 270000 one, 4.42 GB, wrote nothing there. Every other function the library calls held at both sizes, tried at the same corner. The library bounds a pixmap's bytes below 2 GiB (`design.md` §4, §5). Found 2026-11-08 at 3fdacef.
33. **A channel outside 0 to 255 is taken where it should be refused.** `get_color` clamps such a channel, `{300, -5, 2, 1}` stored as `{255, 0, 2, 1}`, wherever epx takes a color. The library refuses a channel outside 0 to 255 before the call (`design.md` §5).
