# Defects found in epx

The defects the library met in epx that its pinned commit has not fixed, each written as a report for epx's tracker, as first filed and numbered 2026-10-20 to 2026-11-17 (`docs/log.md`, *The first cut built*, *The reports verified*, *The fixes verified*, *The sentences for 3fdacef*, *A pixmap across nodes and under load*, *The calls from many processes*). The numbers are those of the first filing, which the design and the log cite; a report goes when the submodule moves to a commit that has its fix (the log's *The pin moved*), so the gaps are what epx fixed.

Each of these stays until a commit of epx the library builds has its fix. Each is an issue of epx's tracker, https://github.com/tonyrog/epx/issues, filed 2026-11-17: 42 is its 6, 44 its 7, 40 its 8, 39 its 9, 41 its 10, 43 its 11 and 33 its 12 (`docs/log.md`, *The reports filed at epx's tracker*).

None blocks a function of the library: each is a wart the library ships around. 33 was found 2026-10-23 trying the edges of `sub`, `scroll`, the rounded rectangle and the polygon (`docs/log.md`, *The four functions*), 39 to 41 on 2026-11-08 at `3fdacef`, the commit the pin moved to that day (`docs/log.md`, *The sentences for 3fdacef*), 42 on 2026-11-17, with two processes on one pixmap (`docs/log.md`, *A pixmap across nodes and under load*), and 43 and 44 the same day, with many processes on one context and one window (`docs/log.md`, *The calls from many processes*).

## Warts

Most serious first: 42 writes and reads outside a pixmap within the library's bounds, where two processes share it; 44 ends the node where two processes first show one pixmap at once; 39 and 41 write wrong where a program cannot tell, each where the library scrolls or scales; 43 draws what no value of a key draws, where one process sets a context while another draws with it; 40 crashes beyond the library's bounds; and 33 takes a channel it should refuse, on a call the library never makes.

42. **A clip set while another process reads or sets it lets a write or a read land outside the pixmap.** `epx_pixmap_set_clip` (`epx_pixmap.c`) stores the clip field by field with no lock, so a call on another scheduler reads the new corner with the old size, and two sets may leave such a clip. One process set a sub-pixmap's clip, four rows of a 64 by 8 argb, between `{63, 0, 1, 4}` and the whole while another called at 70, 3, which neither holds: each function that writes within a clip but `pixmap_put_pixels` wrote the parent below, and `pixmap_get_pixel` and the area functions read there. On a 2048 by 2048, calls at 4000, 4000, `pixmap_put_pixels` among them, touched memory 16 MB past it, crashing the VM in 1 run of 4. `pixmap_draw` drew columns outside both clips. The library states it (`design.md` §4, §11). Found 2026-11-17 at 3fdacef.
44. **A draw queued ahead of its pixmap's attach hands `XPutImage` no image.** `pixmap_attach` (`epx_nif.c`) sets `pixmap->user` before it queues the attach, and `pixmap_draw` takes any pixmap whose `user` is set, so a draw from another process may reach the backend's queue first. `x11_draw` (`epx_backend_x11.c`) then reads `pixmap->opaque`, still NULL, checks the window alone and passes it to `XPutImage`. Two processes each read `pixmap_info_(P, backend)`, called `pixmap_attach(P)` where it answered `undefined`, and then `pixmap_draw`, on a fresh 128 by 128 argb pixmap, 5000 pixmaps a run: the VM crashed in 6 runs of 8 on a quiet machine, each within a second, in 6 of 10 on a loaded one, and in 4 of 6 under the address sanitizer, each a read at address 0 in `XPutImage` from `x11_draw`. The library states it (`design.md` §12). Found 2026-11-17 at 3fdacef.
39. **A scroll between two pixmaps by both amounts shifts the whole target horizontally.** `epx_pixmap_scroll` (`epx_pixmap.c`) scrolls vertically from the source into the target within their common area, then horizontally on the target alone, whose common area with itself is the whole target: `pixmap_scroll(S, T, 1, 1, false, Fill)` with `S` a numbered 2 by 2 and `T` a 4 by 4 filled with one color left every row of `T` shifted right by one and its column 0 filled, rows 2 and 3 among them, and with `true` every row wrapped across all four columns. A target no wider and no taller than the source is right. The library states it (`design.md` §4). Found 2026-11-08 at 3fdacef.
41. **`pixmap_scale` leaves its last rows black at a large height.** `epx_pixmap_scale_area` (`epx_pixmap.c`) steps the source's row by a `float` increment once a target row, `ysf += ys`, and the accumulated error carries the last rows past the source's edge, where `epx_interp` answers transparent black: a 4 by 4 pixmap scaled into 4096 by 70000 has its last two rows `{0, 0, 0, 0}`, into 4096 by 131072 none, into 131073 one and into 140000 two. The library states no pixel rule for `scale` (`design.md` §4). Found 2026-11-08 at 3fdacef.
43. **A draw reads a key of its context more than once, and a `gc_set` between two reads draws what neither value does.** `epx_pixmap_draw_point` (`epx_draw.c`) loads the foreground once for the color and once for the alpha: with `[blend]` and the foreground set between `{64, 255, 0, 0}` and `{192, 0, 255, 255}`, one point in 70,000 was one's color at the other's alpha. `epx_pixmap_draw_ellipse` chooses the border's path on one read of `border_width` and `epx_draw_ellipse_border` (`epx_ellipse.c`) draws with a second: with no fill and the width set between 0 and 65539, one ellipse in 100 drew nothing. `epx_poly_draw` (`epx_poly.c`) reads `fill_style` again for each row: set between `[blend]` and `[]`, half the polygons had rows written solid. Each showed in 4 runs of 4, with nothing outside the pixmap. The library states it (`design.md` §9). Found 2026-11-17 at 3fdacef.
40. **`pixmap_fill_area` computes its address in an `int`.** `epx_pixmap_fill_area` (`epx_pixmap.c`) takes `pixmap->data + r.xy.y*wb + r.xy.x*psz` with `wb` and the coordinates `int`, where every other function takes `EPX_PIXEL_ADDR`'s `ptrdiff_t`: on a 4096 by 140000 argb pixmap, 2.29 GB, `pixmap_fill_area(P, 4093, 139997, 2, 2, C)` crashed the VM, and on a 4096 by 270000 one, 4.42 GB, wrote nothing there. Every other function the library calls held at both sizes, tried at the same corner. The library bounds a pixmap's bytes below 2 GiB (`design.md` §4, §5). Found 2026-11-08 at 3fdacef.
33. **A channel outside 0 to 255 is taken where it should be refused.** `get_color` clamps such a channel, `{300, -5, 2, 1}` stored as `{255, 0, 2, 1}`, wherever epx takes a color. The library refuses a channel outside 0 to 255 before the call (`design.md` §5).
