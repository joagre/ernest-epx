# Defects found in epx

The defects the library met in epx that its pinned commit has not fixed, each written as a report for epx's tracker, as first filed and numbered 2026-10-20 to 2026-10-25 (`docs/log.md`, *The first cut built*, *The reports verified*, *The fixes verified*). The numbers are those of the first filing, which the design and the log cite; a report goes when the submodule moves to a commit that has its fix (the log's *The pin moved*), so the gaps are what epx fixed.

Each of these stays until a commit of epx the library builds has its fix.

Two parts: what blocks a function of the library, and the warts the library states as epx has them and ships around. 26 to 35 were found 2026-10-23 trying the edges of `sub`, `scroll`, the rounded rectangle and the polygon, and 36 to 38 on 2026-10-25 by the release's code reader (`docs/log.md`, *The four functions*, *The release 0.2.0*).

## Blocking

`sub` is held back until these two are fixed, since a flip of a sub-pixmap or a copy into one corrupts memory and no call can tell a sub from a pixmap (`plan.md`, milestone 9).

36. **`pixmap_flip` of a sub-pixmap swaps the parent's row length, not the sub's width.** `epx_pixmap_flip` (`epx_pixmap.c:1991`) swaps `bytes_per_row` bytes a row from the sub's corner, so the flip writes the parent's pixels beside the sub and past the parent's last row: on a numbered 4 by 3 `rgb` pixmap, flipping `sub_pixmap(P, 1, 0, 2, 3)` gave `[1,10,11,12,0,6,7,8,9,2,3,4]` where `[1,10,11,4,5,6,7,8,9,2,3,12]` is right, the 0 read past the memory; `flip` of `sub_pixmap(create(2000, 2000, argb), 1990, 1000, 10, 1000)` run 200 times aborted the VM with `free(): invalid pointer`. Found 2026-10-25 at 02a0eaf.
37. **`pixmap_copy_to` into or from a sub-pixmap copies `sz` bytes in one run.** Where width, height, `sz` and format are equal, `epx_pixmap_copy_to` (`epx_pixmap.c:2094`) copies `src->sz` bytes at once, and a sub's `sz` is the parent's row length times its height, so a sub nearly as wide as its parent meets the test: copying a 2 by 2 pixmap into `sub_pixmap(P, 1, 1, 2, 2)` of a numbered 4 by 4 zeroed the parent's `3, 1`, `0, 2`, `3, 2` and `0, 3`, and at the parent's last row the write runs past its memory; a copy from such a sub reads past it the same way. Found 2026-10-25 at 02a0eaf.

## Warts

Most serious first: 26 crashes on a call the library never makes, and 30 holds a scheduler for a polygon's whole height; 12, 23, 25, 27, 28, 31, 32 and 35 draw or write wrong where a program cannot tell, 24 shows memory and 38 writes nothing where it cannot allocate, each where the library draws.

7 crashes, 8 writes nothing and 19 refuses silently, each beyond the library's bounds; 5 answers memory, 29 moves a polygon under a transform and 33 takes a color it should refuse, each on a call the library never makes; 34 raises the wrong error on a type the library's signature forbids.

12. **An ellipse's ring is malformed at its top and bottom.** `epx_draw_ellipse_border` with a border of 1 or 2, and past a radius of 65535, draws a lone pixel outside the ring, lets the fill show through below it, and makes the ring thicker there than at the sides: a 20 by 20 ring's second row is one pixel where the filled circle's is seven. The library states the ring as epx draws it (`design.md` §9).
23. **An ellipse of even width or height is one pixel larger.** `epx_ellipse.c` takes `x + 2*a` as the right edge, so an ellipse 20 wide at `x` 1 covers columns 1 to 21, as one 21 wide does, and the same for its height. The library states the size as epx draws it (`design.md` §9). Found 2026-10-23, at 1377959 and 23a0ed2 alike.
25. **A diagonal line of width 1 leaves out its first pixel.** `pixmap_draw_line(P, Gc, 0, 0, 5, 3)` draws `1, 1`, `2, 1`, `3, 2`, `4, 2` and `5, 3` and not `0, 0`, whatever the line's style, where a horizontal or vertical line keeps both ends; `nfirst` and `nlast` change nothing for a single line; a polygon's outline leaves out an end of each such edge too, the upper one (35). The library states it (`design.md` §9). Found 2026-10-23, at 1377959 and 23a0ed2 alike.
24. **A window's copy off the screen is never cleared.** After a draw, the parts of the window not drawn into show what the X server's memory held, `17, 2, 19` where the background was white. The library states nothing of what a new window shows (`design.md` §11). Found 2026-10-23, at 1377959 and 23a0ed2 alike.
7. **The area functions take their row stride as an `int`.** `epx_fill_area(uint8_t*, int dst_wb, ...)` and its kin, so `pixmap_create(600000000, 2, argb)` is taken and `pixmap_fill_area(P, 0, 0, 1, 2, C)` crashes the VM. The library bounds a pixmap's bytes below 2 GiB and a coordinate at 16777216 (`design.md` §4, §5).
8. **A width that rounds to 2^32 writes nothing.** `get_dim` converts with `(unsigned int) round(wf)`, so `pixmap_fill_area(P, 1, 0, 4294967295, 1, C)` writes nothing where it covers the pixmap. The library bounds a width at 16777216 (`design.md` §4).
19. **A window wider than X takes is refused silently.** `window_create` with a width of 40000, 70000 or 16777216 answers a window, and `window_attach`, `window_sync`, `pixmap_draw` and `window_detach` each answer `ok`, with no window on the screen and `window_info` reporting the width asked. The library bounds a window's width and height to 1 to 32767 (`design.md` §11).
5. **An empty `pixmap_get_pixels` answers the pixmap's live memory.** `pixmap_get_pixels(P, 0, 0, 0, 0)` is the shortcut for every pixel with its alignment, as the C comment says, and answers a binary over the pixmap's own memory, 32 bytes for a 2 by 2 pixmap, uninitialized before the first fill and changing as the pixmap is written, which no documentation states. The library answers no bytes for an empty rectangle without calling epx (`design.md` §4).
26. **A sub-pixmap whose parent was collected crashes the VM when asked for its parent.** `pixmap_dtor` leaves `pixmap->res` pointing at the freed resource, and `pixmap_info(Sub, parent)` builds a term from it: with 200 subs whose parents were dropped and collected, the call crashed 3 of 3 runs. The pixels are fine, read and written through the sub after the parent's collection. The library's `sub` is held back from 0.2.0 until 36 and 37 are fixed (`plan.md`, milestone 9), and will never ask a pixmap for its parent.
27. **A scroll between two pixmaps by both amounts loses the vertical one.** `pixmap_scroll(Src, Dst, 1, 1, false, Fill)` with `Src` and `Dst` distinct writes what `(1, 0)` writes: the horizontal step reads `Src` again and overwrites the vertical result. On one pixmap both apply, vertical first. The library states a scroll between two pixmaps by both amounts as not stated (`design.md` §4).
28. **A scroll by 0 and 0 into another pixmap copies nothing**, where a wrap by a whole width or height copies the source into the target. The library states it (`design.md` §4).
29. **`pixmap_draw_poly` applies a translation twice.** The `0`, `0` offset of `draw_poly/3` goes through the pixmap's transform as the vertices do: with the pixmap translated by `(2, 1)`, a square at `(2, 1)` landed at `(4, 2)`. The library sets no transform.
30. **A filled polygon scans every row of its height whatever the clip**, holding its scheduler meanwhile: a filled polygon 10 by 10^8 on a 16 by 16 pixmap took 8.8 s, about 88 ns a row, where its outline and a rounded rectangle of the same size return at once. The library states a filled polygon's cost as its height in rows (`design.md` §9), about 1.5 s at its bound of 16777216.
31. **A rounded rectangle's border placed inside is a row thicker at the top and the bottom than at the sides**, and its fill loses a row at each: with radii 0 on 12 by 9, a border of 1 measured 2 rows at the top against 1 at the left, 2 measured 3, and 3 measured 4, where `pixmap_draw_rectangle` with the same context measured 1, 2 and 3; 12 by 8 with a border of 3 is drawn wholly in the border's color where a rectangle leaves a 6 by 2 fill.

    The rasterizer is `epx_draw_rrect_ring`, which gives the ellipse's ring its marks too (12). The library states it (`design.md` §9).
32. **A polygon's outline blends each vertex twice.** With a blended line style, a vertex came out as `{159, 0, 0, 191}` against `{191, 0, 0, 127}` mid-edge; the C carries `// FIXME: do not draw pixel twise!`. The library states nothing of it: a program that blends an outline sees it.
33. **A color is taken where it should be refused.** `get_color` takes an unknown color name, `nosuchcolor`, as `{255, 0, 0, 0}`, and clamps a channel outside 0 to 255, `{300, -5, 2, 1}` stored as `{255, 0, 2, 1}`, wherever epx takes a color. The library sends no name and refuses a channel outside 0 to 255 before the call (`design.md` §5).
34. **`pixmap_draw_poly` with a list that is not one raises `function_clause`**, not `badarg` as every other wrong argument does. The library's signature gives it a list.
35. **A polygon's diagonal edge leaves out its upper end, whichever end comes first.** `map_edge` orders each edge's ends by `y` before `epx_draw_line`, so the end of the smaller `y` is the line's first pixel and is left out (25): the outline of `[{0, 0}, {6, 0}, {6, 6}, {3, 3}, {0, 6}]` at width 1 lacks the vertex `3, 3`, and `[{0, 0}, {3, 3}]` and `[{3, 3}, {0, 0}]` draw the same three pixels without `0, 0`. The library states it (`design.md` §9).
38. **A wrapped scroll writes nothing where its buffer cannot be allocated.** `shift_area_rotate` and `scroll_vertical` copy the wrapped columns or rows, up to almost the whole pixmap, into a `malloc`ed buffer, and where `save` is `NULL` they return with nothing written and `ok` answered. The library states it (`design.md` §4). Found 2026-10-25 at 02a0eaf.
