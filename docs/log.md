# Decisions

The dated rationale for the design and the plan, newest last, and what was rejected. Never normative: the design says what the program is, and the plan what is built when. An entry says what was decided, the principle of the report's §0 that decided it, and what would change it.

## Begun from the template

*2026-10-20.* The repository was begun from `ernest-template` at its tag `v0.1.0`, whose `CLAUDE.md`, `docs/style.md` and `tools/docs.ern` are refreshed from there and not edited here. The way of working is the template's; a change to it goes to the template first. The library is the first repository begun from the template, so what the copy teaches about the template goes back to it: the first lesson is that a dependency that is Erlang, epx itself, is not what `make lib` fetches, which the entry below decides.

## epx and tree_db as submodules

*2026-10-20.* epx and tree_db are read-only git submodules under `erl/`, pinned to a commit each, built by their own `make` and linked under `lib/` as `ebin` and `priv`, so that the load path, which `ern run` adds to the host's code path, lets the host find epx's NIF from `priv/` beside `ebin/`. A copy of the trees was rejected: it loses where the code came from and drags epx's C into this repository. A fetch by rebar3 was rejected: epx's build is its own Makefile, its port configuration is rebar2's, its tree_db dependency is unpinned, and rebar3 is not on the machine. Principle 2, one way to bring in Erlang, the host's own, and the template's `lib/` kept as the one place a program loads from. Tried before being written: a pixmap made, filled red and read as `#(255, 255, 0, 0)` from a scratch program. What would change it: a dependency tool of Ernest's, the template's proposal's fourth ask of the language.

## The first cut built

*2026-10-20.* Built by an agent from the decided proposal, read back whole, and closed with these decisions, each where the proposal was silent or epx was not what it guessed. Tried first, each edge of the proposal's section 4 against the NIF: epx answers opaque black for a read outside the pixmap, clips a write, clamps a channel and does not mask it, and crashes the VM on a sub-pixmap's coordinates, on a scroll past the width and on an unsupported format name, which `epx_bugs.md` records as reports.

`sub` and `scroll` are left out until epx is fixed, since a function that can crash the node is no function: principle 1. A new pixmap is filled with 0, one pass over its pixels, since epx leaves the memory as the host gave it and a program would read what a last run left: principle 1. `putPixels` faults on bytes of the wrong size, where epx writes nothing or reads past them, and an alpha or a fade outside 0 to 255 faults as a channel does, where epx takes anything above as 255: decision 5 of the proposal applied to each, principle 1. An empty `getPixels` answers no bytes without the call, since epx answers its live memory. `getPixel` outside the clip answers opaque black as epx does, documented and not made an `Optional`, since the shim is the host function exactly and the clip is the caller's own setting. The clip is not read by `fill`, `flip`, `copyTo` and `getPixels`, as epx has it, documented.

The five area operations read the source's clip and move the target's corner before the call, since epx cuts the source's rectangle at the clip without moving the target's and the pixels land wrong (`epx_bugs.md` 6). The cost is stated and not hidden: about twice a small area operation, 96 to 253 ms over 200,000 one-pixel copies and 140 to 296 ms over 32 by 32; whether it stays is the plan's milestone 2 decision 1. A test's comment, not a doc block, names the design section it covers, since a doc block puts the test on the module's page: the template's rule changed with it.

## The clip correction dropped

*2026-10-20.* The five area operations call epx's functions exactly, and the correction that read the source's clip and moved the target's corner before each call is gone: a shim is the host function exactly, and what Ernest adds costs a fraction of the host's operation, where the correction cost a call of its own and doubled a small area operation. What epx does with a source rectangle that begins outside the source's clip, cut to the clip and landed as if it were not, is stated in `design.md` §4 and in each operation's doc block, so that a program begins the rectangle within the clip and nothing is hidden: principle 1 satisfied by the sentence rather than by code. `epx_bugs.md` 6 is the report; when epx fixes it, the sentence goes.

## The release review

*2026-10-20.* The release 0.1.0 ran as `release.md` says. A fresh recursive clone built and passed in a minute. Two readers, each a session of its own, a cold one over the README, the examples and the page and a code reader over the module against the design and Appendix E.0's shape rules, handed in thirty-six findings, which `findings.md` held with a verdict each until every line was done, planned or dropped, and then went; their language parts went straight to Ernest's `language_feedback.md` as its 125 to 132.

What the fixes decided. A coordinate is bounded to plus or minus 16,777,216 and a width or height to 16,777,216, and a pixmap's bytes to below 2 GiB, each refused in Ernest before the call with its own cause, since epx turns a coordinate into a float and computes a pixmap's bytes and a pixel's address in 32 bits, which silently lands a far pixel wrong or crashes the node (`epx_bugs.md` 7 and 8): principle 1. A width or height below 0 reads and writes nothing, as §7.4 and the standard library have a count below 0, where epx raised: principle 1 again, the reader who knows `List.take`. tree_db went, since only epx's windows reach it and no pixmap function does: principle 5. What `scale` writes from a clipped source and what a blend writes when its two rectangles overlap in one pixmap are not stated, each said so on the page rather than closed in code, as the clip correction was dropped. A call runs on the host's scheduler until it ends, said on the page as a cost the name does not suggest. The page's wording was put right where the cold reader read it wrong, the Xor arithmetic, the fade at 255, an opaque source one short.

What the review taught the template is `TEMPLATE.md`'s, its `v0.5.0`; a tool that holds a page to its `// =>` examples is wanted and waits there.

## The ray tracer

*2026-10-20.* The proposal `proposals/raytracer/proposal.md` decided as recommended. The example exists to show a pixmap shared by capture and written by every worker, so the workers write into it and send nothing back: principle 3, the sharing visible in the program's shape. Rows in turn rather than blocks, so that the sphere's slow rows are spread; the worker count on the command line, since Ernest has no function for the host's scheduler count and the count is what shows the speedup; a faulting worker ends the program rather than leaving a half-black picture: principle 1. Depth, size and anti-aliasing fixed in the program, since an example carries no options: principle 5.

## Where the Library Stops

*2026-10-20.* A 2-D library of pixmaps and pixels, and nothing more: the Utah teapot needs a mesh read from a file and a bounding-volume tree, each a library's work by the rules, a textured picture needs `epx_image`'s adapter, and a picture drawn on the screen as it is traced needs epx's windows and events, which were cut out at the first proposal and stay out: principle 2, one job, and principle 5. What a richer picture can be within one program is Whitted's spheres, milestone 5. The progressive render is noted for a windows library, where it would be the first example, since the tracer's workers already write row by row.

## A Window That Shows

*2026-10-20.* *Where the Library Stops* kept every window out; this keeps the half of a window that only shows. A window that shows a pixmap is six foreign functions of the shape `Epx` already has, epx's backend started, a window made and attached, a pixmap attached, drawn into it and synced, and nothing comes back across the boundary where the window is made with no event flag, so the question that kept windows out, an Erlang message shape no Ernest type names, does not arise. What it buys is the picture the library exists to teach: eight workers writing their rows into one pixmap, seen as they write. Receiving from the window stays out, and would stay out even as a later cut, since it is Ernest's question before it is epx's: principle 2, one job, the window shows. Decided with the user.

## The second cut built

*2026-10-20.* Built by an agent from the decided proposal, read back whole, and closed with these departures, each argued here. The context's type is `Epx.Context`, declared in `Epx`, and the setters are `Epx.Gc`'s: a type `Gc` beside a module `Epx.Gc` is refused, since the namespaces coincide (§4.2), `Epx.Gc.Gc` would be named for its module, and a type in `Epx.Gc` that `Epx`'s drawing functions take makes a cycle (§4.1); the drawing functions stay in `Epx`, the pixmap their subject, and `Epx.Gc` keeps its own copies of the width and color checks, a cost carried to Ernest as feedback 135. Five drawing functions, not seven: the rounded rectangle is lopsided and hangs at large sizes and the polygon crashes the node on an empty list and leaves debugging colors in a fill (`epx_bugs.md` 13 and 14), and a function that can crash the node is no function: principle 1, as `sub` and `scroll`. `Style` is `Solid`, `Blend` and `Antialiased`, the fill's an `Optional` with `None` for no fill: `Sum` draws as `Solid` everywhere and `none` is refused for a border, so neither is a way to say anything: principle 2. The background key is out until the text cut, which alone reads it. The border is placed inside, `[solid, inside]`, since epx's default placement moves the whole rectangle a pixel right and down (report 11) and inside is exact: principle 1. An ellipse's width and height are bounded at 131071, where epx's arithmetic overflows (report 12). `drawTriangle` numbers its corners as `drawLine` numbers its ends.

A wide horizontal or vertical line is filled in Ernest through `pixmap_fill_area`, since epx's band writes past the clip and past the pixmap's memory (report 9); it costs about 2.6 times epx's line, 0.17 to 0.45 µs, and a diagonal or one-pixel line costs nothing more. It stands as the plan's milestone 2 decision 8, since the clip correction was dropped for a cost of the same kind, where that one corrected a misplacement and this one prevents a write outside memory. The clock face's hands are triangles, since a wide diagonal line lies beside its line (report 10), and its time is UTC, since the library has no local time.

## The window decided

*2026-10-20.* The proposal `proposals/window/proposal.md` decided as recommended. Four functions and nothing kept in the module, since a window is epx's resource as a pixmap is: principle 5. The word `show` on an example's command line, since the examples already take their arguments there and the PPM stays for `make test`: principle 2, one way. Enter closes, a wait on what it means, since the window takes nothing back. Each ray-tracer worker shows its own row, which is the demonstration, if a draw from any process is taken. No test under `make test`, since a test cannot look at a screen and one that passes without a display would say nothing: principle 3, tried by hand and said so. The experiment in Erlang first, since whether a window without event flags receives any message decides whether the module can exist at all.

## tree_db Returns

*2026-10-21.* The release review dropped tree_db since no pixmap function reaches it, which was right for the pixmaps and wrong for the window: `epx.app` declares tree_db among the applications epx depends on, and `Epx.Window.open` starts epx's application, which the host refuses to start without its declared dependency. So tree_db is a submodule again, built and on the load path at run time, named in `THIRD_PARTY_LICENSES` and the acknowledgments; its repository states no license, which is asked of its author and said in the file meanwhile. A dependency an application declares is needed whether a function reaches it or not: principle 1, the lesson.

## The window built

*2026-10-21.* Built by an agent from the decided proposal after its experiment, read back whole, and closed with five departures. The module is `Epx.Screen` and the type `Epx.Screen.Window`, not `Epx.Window`: shape rule 7 refuses a type named for its module, `Epx.Window.Window`, and §4.2 refuses a type `Window` in `Epx` beside the module `epx/window.ern`, so the module is named for its domain and the type for what it is, as `Tcp.Socket` and `Ets.Table` are: principle 1, the reader predicting `open` to answer a `Window`; the gap is Ernest's feedback 136. `close` hides the window through `window_adjust` rather than `window_detach`, since a draw issued before a detach is processed crashes the node (`epx_bugs.md` 17), and the host's collection detaches it safely later. `open`'s bounds are X's, 32767, and `showArea` cuts at them so that nothing wraps (19, 20); `Rgba` and `Abgr` are refused, since the backend shows their channels misplaced (18). `show` never syncs, since a draw is on the screen without one and `window_sync` answers the maker with a message.

The experiment broke the proposal's premise: epx sends the process that opened a window `{epx_event, Window, close}` when its close button is pressed, whatever the window's flags (16), and the library cannot prevent it. Under Ernest a `receive` whose patterns name constructors leaves it in the mailbox, and one whose pattern is a variable takes it as a message of the mailbox's type, which §8.4 says cannot happen: a defect of Ernest's, carried as its feedback 137. The window stays, with the page saying that a program opens it in a process that receives nothing or whose patterns each name a constructor, as the four examples do; a close button that closes waits on both Ernest and epx. Decided with the user.
